# 静悦小程序产品与技术方案

> 版本：v1.0  
> 日期：2026-10-28  
> 目标：在现有 ZRAdminNetCore + 静悦业务模块基础上，建设员工使用的移动工作台，而不是照搬 Web 管理后台。

## 1. 结论先行

### 1.1 产品定位

小程序定位为 **门店员工工作台**，服务现场经营与客户跟进，核心闭环是：

```text
到店/跟进 → 查会员 → 找货/扫码 → 开单/预定 → 待办与复盘
```

小程序不是 Web 后台的手机版。它的价值在于移动、扫码、拍照、快速记录和即时提醒，不是批量配置、复杂报表或系统管理。

### 1.2 推荐技术路线

- 保留现有 `静悦工作台_uniapp` 作为小程序前端基础，不做第二套 uni-app 工程。
- 后端统一使用 `ZR.Admin.WebApi` 作为唯一业务事实源。
- 员工使用现有账号密码登录，不接微信 OpenID，不做微信身份绑定。
- 请求沿用现有 JWT：`Authorization: Bearer <token>`，必要时带租户头 `tenantId`。
- 小程序端只保留安全的离线草稿/读取缓存；销售、库存、会员、权限等正式数据以服务端为准。
- 微信云开发不再作为正式业务数据源，相关同步入口从员工产品中移除。

### 1.3 必须先纠正的问题

现有 uni-app 原型的数据主体是本地 SQLite + 微信云开发，而 Web 端使用 `ZR.Admin.WebApi`。如果直接发布，会导致：

- Web 与小程序会员、库存、销售数据不一致；
- 每台手机形成一份独立数据；
- 服务端权限、审计、租户隔离失效；
- 老板在 Web 看到的经营数据与店员手机不一致。

因此正式开发顺序必须是：先统一账号与数据源，再做业务页面。

## 2. 小程序功能范围

### 2.1 首期必须上线（P0）

| 模块 | 小程序能力 | 原因 |
| --- | --- | --- |
| 登录与会话 | 账号密码登录、退出、Token 失效重登、当前门店 | 上班即用，必须稳定 |
| 今日工作台 | 今日待办、待取货预定、生日提醒、库存预警、销售摘要 | 员工打开先知道今天做什么 |
| 待办 | 查看、新增、完成、编辑、按日期/优先级筛选 | 高频、适合移动端 |
| 会员 | 搜索、查看档案、消费历史、积分、跟进记录、新增跟进 | CRM 核心 |
| 库存 | 按名称/条码搜索、查看货品详情与状态、扫码找货 | 现场高频，移动端优势明显 |
| 销售开单 | 扫码/搜索选货、匹配会员、预览、提交、查看我的单据 | ERP + CRM 的核心闭环 |
| 预订单/定制定金 | 查看待取货、更新备货状态、登记定金/预定 | 门店现场高频 |
| 消息 | 待办到期、预定取货、生日、库存预警、审批/异常提醒 | 让员工不用反复查后台 |
| 我的 | 个人资料、当前门店、修改密码、退出登录 | 基础账户能力 |

### 2.2 第二期增强（P1）

| 模块 | 能力 | 说明 |
| --- | --- | --- |
| 入库草稿 | 扫码/搜索货品、拍照、录成本售价、保存草稿 | 复杂确认仍建议 Web/店长完成 |
| 销售退货 | 查原单、发起退货、上传凭证 | 由权限决定是否允许确认 |
| 盘点 | 扫码盘货、差异记录、提交盘点点 | 必须服务端校验，避免重复提交 |
| 经营摘要 | 今日/本月销售额、客单、件数、目标进度 | 只做轻量图表，不做大表格 |
| 目标 | 查看目标、更新进度、关联待办 | 复杂目标配置留在 Web |
| 话术库 | 查看、复制、按标签/分类筛选 | 不做大量编辑 |
| 客户标签 | 查看与维护常用标签 | 高价值标签由 Web 统一管理 |

### 2.3 留在 Web、不要放入小程序

- 用户、角色、菜单、部门、岗位、权限配置；
- 租户、套餐、系统参数、数据字典维护；
- 批量导入导出、历史数据修复、复杂查询与报表；
- 编号规则、打印模板设计、门店打印代理；
- 活动完整配置、奖励规则批量设置；
- AI 复盘/全局分析；
- 微信云开发同步、数据库备份、CSV 手工导入。

### 2.4 不建议首期做

- 微信支付、会员在线充值；
- 多组织调拨、退库、跨店库存流转；
- 完整审批引擎；
- 积分兑换商城；
- 小程序内标签打印；
- 复杂 BI 大屏。

## 3. 信息架构

### 3.1 底部导航（5 个主入口）

```text
首页       业务        [扫码/开单]       消息       我的
```

中间按钮不是普通 Tab，而是快速动作入口：

- 扫码开单
- 新建预定
- 新增会员/跟进

### 3.2 首页“今日工作台”

按“先做事、再看数”排序：

1. **当前门店与身份**：姓名、门店、岗位、切换门店（有权限时）。
2. **今日关键数**：今日销售额、成交单数、我的待办数、待取货数。
3. **今日待办**：按截止时间/优先级排序，支持完成和新增。
4. **待取货预定**：今天、明天、逾期三组。
5. **客户提醒**：生日、长期未跟进、待回访。
6. **库存提醒**：缺货、低库存、锁定/异常货品。

### 3.3 业务页

按员工真实任务分组，而不是按数据库表分组：

```text
会员与客户
  搜索会员 / 新增会员 / 跟进记录 / 客户标签

库存与销售
  扫码找货 / 库存查询 / 快速开单 / 我的销售单 / 退货(有权限)

预定与到货
  预订单 / 待取货 / 定金登记 / 到货通知

目标与复盘
  我的目标 / 目标进度 / 日周复盘
```

### 3.4 消息页

消息必须可追溯到业务对象，不允许只显示一段无语境文本：

- 待办到期/被指派；
- 预订单到货/取货；
- 客户生日/回访；
- 库存预警；
- 销售单异常/退货；
- 账号或权限变更。

### 3.5 我的页

只放个人信息与会话管理：

- 姓名、账号、角色、门店；
- 修改密码；
- 当前门店切换（后端授权）；
- 通知偏好；
- 退出登录；
- 版本信息。

不放“数据同步”“数据字典”“AI 复盘”“云环境检测”等系统配置。

## 4. 角色与入口

### 4.1 建议角色

| 角色 | 小程序重点入口 |
| --- | --- |
| 导购/店员 | 今日待办、会员、库存查询、扫码开单、预定、消息 |
| 店长 | 店员能力 + 本店经营摘要、预定确认、退货、盘点和入库草稿 |
| 库管 | 库存、扫码找货、入库草稿、盘点、库存预警 |
| 运营 | 会员标签、话术、活动查看、客户跟进 |
| 管理员 | 默认不用小程序做系统配置；如需使用，只开放查看与应急处理 |

### 4.2 权限实现原则

- 继续使用 `sys_user / sys_role / sys_menu`，不新增移动端权限表。
- 沿用 `jingyue:<module>:list/query/add/edit/remove/confirm/export` 权限编码。
- 入口显示由后端返回的权限集合决定，不只依赖前端隐藏。
- 所有写接口必须在后端再次校验权限、租户、门店和数据范围。

## 5. 关键业务流程

### 5.1 账号密码登录

```text
输入账号 + 密码 + 租户(如有)
  → 前端 MD5 密码
  → POST /login
  → 保存 JWT
  → GET /getInfo 获取用户、角色、权限
  → 获取可访问门店
  → 选择/确认当前门店
  → 进入首页
```

约束：

- 不接微信 OpenID。
- 不在前端持久化明文密码。
- Token 过期统一跳登录页，保留上次账号但不保留密码。
- 多租户部署时租户字段必填或记住上次选择；单租户固定主租户。
- 单设备登录现状会导致 Web 登录挤掉小程序，必须验证并决定是否对移动端例外，或产品上接受单设备会话。

### 5.2 扫码开单

```text
扫条码/货品编码
  → GET jingyue/sale/goods?keyword=<code>
  → 展示唯一货品或候选
  → 匹配会员(手机/姓名/会员号)
  → 选活动、会员折扣、调价/抹零
  → POST jingyue/sale/preview 计算金额
  → 确认提交 POST jingyue/sale
  → 如需店长确认，再 POST jingyue/sale/{id}/confirm
```

现有后端已支持按 `Barcode/GoodsNo` 精确找货，能作为小程序核心流程的基础。

### 5.3 会员跟进

```text
搜索会员 → 会员详情 → 新增跟进(文字/图片/下次回访)
  → 保存会员跟进 → 根据回访时间生成员工待办/提醒
```

注意：不要把“客户画像”和“销售单”做成两套客户表，销售开单仍需写入/匹配 `jy_member`。

### 5.4 预订单到货

```text
员工查看预定 → 标记到货/待取货 → 通知客户(站内/短信/人工)
  → 取货核销生成正式销售单
  → 库存、积分、转介绍只走销售单过账
```

预订单不能直接扣库存，沿用现有“核销生成销售单”的业务决定。

## 6. 后端改造清单

### 6.1 必须做

1. **统一业务数据源**
   - 移除小程序云开发作为正式数据来源。
   - 新增 uni-app API 适配层，统一走 `ZR.Admin.WebApi`。

2. **补齐会话基础设施**
   - JWT 存取与自动刷新/过期处理；
   - 统一 401/403/480 处理；
   - 登录失败限流与日志保留。

3. **门店授权**
   - 新增“我的可访问门店/当前门店”接口；
   - 后端从用户角色、部门数据范围计算可访问门店；
   - 禁止直接信任客户端传入的任意 `StoreId`；
   - 所有 `StoreId` 查询和写入校验归属。

4. **移动端聚合接口**
   - `GET mobile/home/summary`：今日指标、待办、取货、生日、库存提醒；
   - `GET mobile/navigation`：按权限返回小程序入口；
   - 减少首屏 N 次请求，控制弱网体验。

5. **移动端上传**
   - 封装小程序图片/文件上传，复用现有 `sys_file` 和上传接口；
   - 限制大小、类型、MIME、扩展名与保存路径；
   - 禁止客户端决定服务器绝对路径。

6. **消息与待办联动**
   - 预定到货、会员回访、库存预警可生成待办/消息；
   - 同业务事件仅生成一次，任务必须具备幂等键。

### 6.2 建议补强

- 统一响应错误码映射，避免小程序只显示“请求失败”；
- 对销售、库存、会员等写操作增加幂等键，防止弱网重试重复开单；
- 关键查询增加分页上限与索引检查；
- 对手机号、微信号、生日等敏感字段做权限/脱敏；
- 增加操作日志中的门店、员工、业务单号。

### 6.3 可暂不改造

- 现有商城 `mms_* / oms_*` 体系；
- 完整工作流引擎；
- 标签打印代理；
- 微信支付；
- Web 端复杂报表布局。

## 7. Uni-app 改造路线

### 7.1 可复用

现有工程已有以下页面和基础组件，可复用其交互、样式和部分业务逻辑：

- `home`、`today`、`todo`
- `customer`、`customer-follow`、`membertags`
- `stock`、`sales`、`preorder`
- `message`、`profile`
- `PageShell`、`TabBar`、`FormPicker`、`DateField`、`CustomerSuggest` 等组件

### 7.2 必须删除或替换

- 微信云开发初始化与同步页面；
- 本地 SQLite 作为正式业务主库；
- CSV 导入、备份恢复、云环境自检；
- 固定 `OWNER = 赵静`、固定店铺名称；
- 数据字典、AI 复盘、日记等非首期能力；
- PC 扫码登录页面（与账号密码需求无关）。

### 7.3 建议目录

### 7.4 前端状态要求

每个页面必须具备：

- 加载态：骨架屏或明确 loading；
- 空数据态：说明为什么为空、下一步做什么；
- 错误态：可重试、保留已输入内容；
- 无权限态：说明联系店长/管理员；
- 弱网态：显示离线草稿或稍后重试，不假装提交成功。

## 8. 数据安全与并发

### 8.1 租户与门店

- `TenantId` 永远由登录上下文和后端配置决定，不信任客户端任意切换。
- `StoreId` 必须先做可访问门店校验，再进入业务查询/写入。
- 店长跨店权限走 RBAC 数据范围；导购默认只看本店。
- 销售、预定、退货、盘点、入库都必须记录操作人和门店。

### 8.2 事务与状态

必须事务化的操作：

- 开单确认、库存扣减、积分/推荐台账；
- 预定核销生成销售单；
- 入库确认生成货品与库存流水；
- 退货回库与金额回退；
- 盘点差异过账。

状态变更必须校验旧状态并做并发保护，例如：

```text
UPDATE ... WHERE Id = @id AND Status = 0
```

受影响行数不等于 1 时提示“单据已变化，请刷新”。

### 8.3 幂等

- 客户端提交开单/入库/盘点时带幂等请求号；
- 服务端对同一用户、业务类型、请求号只处理一次；
- 弱网超时不自动盲目重试写操作，先查询结果。

### 8.4 敏感信息

- 不记录密码、Token、微信 Secret；
- 手机号、微信号、生日按权限展示；
- 图片/视频上传做类型与大小校验；
- 日志只记录必要的业务 ID 和操作结果。

## 9. 发布与验收

### 9.1 P0 验收标准

- 账号密码登录成功，Token 过期可重新登录；
- Web 新增会员后，小程序立即可查；小程序开单后 Web 可见；
- 门店员工不能查看/修改非授权门店数据；
- 扫码能找到唯一货品，库存状态不正确时禁止开单；
- 开单预览金额与服务端最终金额一致；
- 弱网重复点击不会生成两张销售单；
- 空数据、加载中、接口失败、无权限四种状态均有明确界面；
- 关键写操作有操作日志和门店/员工归属。

### 9.2 建议上线节奏

**第 1 阶段：基础设施（必须先完成）**

- uni-app 接入账号密码登录和后端 API；
- 统一请求、会话、错误处理；
- 可访问门店与当前门店；
- 首页聚合接口；
- 删除云同步正式依赖。

**第 2 阶段：员工高频闭环**

- 首页、待办、会员、库存查询、扫码开单、预订单、消息、我的。

**第 3 阶段：店长增强**

- 经营摘要、退货、盘点、入库草稿、目标与复盘。

**第 4 阶段：发布与运营**

- 真机兼容、弱网、权限矩阵、日志审计、灰度发布和数据核对。

## 10. 当前实现状态与本方案差距

### 已有基础

- `ZR.Admin.WebApi` 已有静悦待办、会员、库存、销售、预定、活动、目标等接口；
- 业务表普遍带 `TenantId`，销售等单据带 `StoreId`；
- 登录返回 JWT，权限使用现有 RBAC；
- 库存/销售查询支持条码和货品编码；
- 现有 uni-app 已有较完整的页面原型和移动端组件。

### 必须补齐

- uni-app 主体仍走本地库 + 微信云开发；
- 小程序尚未接入 ZRAdmin JWT；
- 门店可访问范围尚未统一到静悦业务查询；
- 首页/导航/消息等移动端聚合接口尚未形成；
- 现有 uni-app 固定个人身份、系统配置页和小程序范围不匹配；
- 扫码开单、图片上传、幂等与弱网策略需要专门实现和测试。

## 11. 最终建议

先不要把现有 uni-app 的 20 多个页面全部搬到生产。按下面的顺序推进最稳：

```text
账号登录
  → 当前门店与权限
  → 统一 API
  → 首页今日工作台
  → 会员查询/跟进
  → 库存扫码查询
  → 扫码开单
  → 预定与消息
  → 店长增强
```

最重要的判断标准不是“页面像不像 ERP/CRM”，而是员工在手机上能否在 30 秒内完成一次真实动作：找到客户、找到货、开一张单、记一次跟进或处理一条待办。

如果首期功能必须再压缩，保留 **登录、首页、待办、会员、库存扫码、销售开单、预定、消息、我的** 这九项即可形成可用闭环；其余功能都可以后续增加。
